# 商品全局化改造计划

## 1. 现状分析
当前系统中，商品（`product_types`）是依附于特定平台（`platforms`）的。这就导致了：
- 在不同平台需要重复创建同名的商品。
- 看板中需要通过复杂的逻辑，将不同平台下的同名商品聚合起来才能进行“跨平台售出”。
- 用户希望商品成为一个“全局”概念：在看板统一创建，然后在所有平台下自动展示，并且取消平台内部的售出按钮（统一在看板操作）。

## 2. 改造方案

### 2.1 数据库结构调整 (SQL Migration)
需要将现有的树状结构 (`平台 -> 商品类型 -> 票据`) 展平为交叉结构 (`全局商品 + 平台 -> 票据`)。
- **新增表**：`global_products` (id, name, created_at)
- **修改表**：`tickets` 增加 `global_product_id` 和 `platform_id`，并移除 `product_type_id`。
- **数据迁移**：将现有的 `product_types` 数据提取为全局商品，并更新现有的票据关联关系，保证数据不丢失。
- **废弃表**：删除原有的 `product_types` 表。

### 2.2 数据类型更新 (`src/types/index.ts`)
- 新增 `GlobalProduct` 类型。
- 更新 `Ticket` 类型，将 `product_type_id` 替换为 `global_product_id` 和 `platform_id`。
- 删除 `ProductType` 类型。

### 2.3 看板页面改造 (`src/pages/Dashboard.tsx`)
- **新增功能**：在“商品全局聚合”区域的标题旁，增加“新增商品”的按钮和弹窗。
- **数据获取**：直接从 `global_products` 表获取所有全局商品，然后关联 `tickets` 表和 `platforms` 表，计算每个全局商品在各平台的库存。
- **售出逻辑**：保持原有的跨平台批量售出逻辑，但数据结构适配新的数据库字段 (`ticket.global_product_id`)。

### 2.4 库存页面改造 (`src/pages/Tickets.tsx`)
- **移除功能**：去掉平台手风琴内部的“新增商品类型”按钮。
- **移除功能**：去掉具体商品旁边的“售出”按钮。
- **列表渲染**：
  - 外层循环：遍历所有 `platforms`。
  - 内层循环：在每个平台下，**全部列出**所有的 `global_products`（即使该平台下该商品库存为0）。
  - 在每个商品条目下，显示对应的“添加进货”按钮，以及该平台+该商品下的具体票据列表。
- **新增进货**：保存时直接写入 `platform_id` 和 `global_product_id`。

## 3. 执行步骤
1. **生成并执行 SQL**：提供一段安全的 SQL 迁移脚本，要求用户在 Supabase SQL Editor 中执行，完成表结构变更和数据迁移。
2. **更新前端 Types**：修改 `src/types/index.ts`。
3. **重构 Dashboard**：更新看板页面的数据获取、聚合逻辑，并添加创建全局商品的入口。
4. **重构 Tickets**：重写库存页面的渲染逻辑，全部列出全局商品，移除平台内创建商品和售出的功能。
5. **测试验证**：确保新增平台时能看到所有商品，确保能正常进货和在看板进行跨平台售出。
